## The DeepSeek workflow — this is now how work gets built

### Launching a builder

    pwsh -NoProfile -ExecutionPolicy Bypass -File <scratch>\dsh-relay.ps1 -Name <job> -Effort high

- Write the brief to `<scratch>\relay\<job>-prompt.txt` **first**.
- `-ExecutionPolicy Bypass` is required; without it the script is refused.
- The brief is passed **by file path, never as an argument**. `npx.cmd` is a cmd
  shim and cmd truncates an argument at the first `&`, `<`, `>` or `|`. On
  2026-09-18 a brief arrived cut at its first `&` and a build ran with almost no
  instructions.
- Output: `<job>.log` (start/exit) and `<job>-attempt1.log` (the whole run; the
  final assistant message is the report, at the end).

### Launching a read-only auditor

    pwsh -NoProfile -ExecutionPolicy Bypass -File <scratch>\dsh-audit.ps1 -Name <job> -Effort high

Same brief convention. It layers
`C:\Users\Sid\.dsh\.agent-presets\jarvis-auditor\agent.cordis.yml` as a profile
patch, because headless has **no agent-preset flag** — presets are a web-UI
concept. It deliberately does not set `DSH_PERMISSION_MODE`, so the sandbox
stays read-only.

**Known limit: a read-only auditor cannot run tests.** `vite` spawns and the
sandbox returns `spawn EPERM`. Every auditor finding is therefore read from
code and must be treated as a *suspect*, not a conviction. On PR #98 the
auditor raised three findings; two were disproved by running one test each. It
is excellent at finding where to look. It cannot settle anything.

## The review tooling — use it, do not hand-roll

`reviewer-tools/mutate.ps1` and `gate.ps1`, on branch
`claude/reviewer-gate-tools`, head `e78b787`. **Not yet merged to main.**

    pwsh -NoProfile -ExecutionPolicy Bypass -File 'C:/Users/Sid/jarvis-gate/reviewer-tools/mutate.ps1' -Spec 'C:/.../spec.json' -GateDir 'C:/Users/Sid/jarvis-pr97'

**Forward-slash Windows paths.** Backslashes are eaten crossing Bash into pwsh
and the script aborts saying the gate directory does not exist.

Spec is a JSON array of `{name, file, find, replace, testPath, expect}`, or
`{name, edits: [{file, find, replace}], testPath, expect}` for a fault that
needs several edits applied together.

What it guarantees, each because of a real failure:

- `find` must match **exactly once**, and the file must provably change, before
  any test runs. A hand-rolled sweep whose pattern matched nothing reported
  SURVIVED three times — a false finding, worse than none.
- Every kill is **re-run with the mutation still applied**. A flake landing on
  the expected test name reads as a clean kill, and nobody questions the result
  they wanted. A kill that does not repeat is `UNCONFIRMED`.
- A test already red at baseline can never be a kill, so a mutation whose
  expected test is flaky-red is `INVALID`, not SURVIVED.
- A non-zero runner exit with nothing named is `INVALID`. SURVIVED may not rest
  on failing to parse English.
- Exit **2** = the sweep produced no usable result. Exit **1** = it worked and
  found something. Those are different claims.

It was itself audited by DeepSeek on high: six findings fixed, two of them bugs
introduced by the multi-edit change. Detail is in the commit messages.

**Do not hand-roll a sweep — and design a control.** On PR #98 a two-edit
mutation came back KILLED, and the fixture edit *alone* turned out to kill the
same test, so the experiment proved nothing. The tool cannot catch a bad
experiment.
