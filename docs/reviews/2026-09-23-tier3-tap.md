# Single-use tier-3 taps

Builder: Codex, 2026-09-23. Base: `a666097ffe6e0b2c99dc83ce29fc43efacdf7f4d`.

## Behavior and design

`ToolAutonomyGate` now calls `D1ToolConfirmationStore.consumeStandingDecision`.
One `INSERT ... SELECT ... ON CONFLICT DO NOTHING RETURNING` checks the principal,
capability, canonical argument fingerprint and tap time while claiming the tap.
Only the insert winner receives the decision id and permission to continue.
`tool_confirmation_consumptions` records the unique decision id and `consumed_at`.
The original answer remains immutable. Backup and restore include the claim.

Expiry is ten minutes from the immutable response's `responded_at`, exclusive at
the deadline. Future taps refuse. The injected clock is sampled at consumption,
after the first autonomy audit, so a slow audit cannot extend a tap's life.
No channel or call-session restriction was added: a Telegram answer can authorize
the same exact action on a call once. Receipts explain that used or expired taps
need a new confirmation.

The newest matching approval is selected. A spent newest tap does not fall back
to an older unused approval for the same action. A new tap authorizes another
attempt. Consumption is not refunded after an audit or tool error: an unknown
side-effect outcome must not become permission to retry. This is at-most-once
authorization, not a promise that an external side effect will complete.

A separate claim table avoids weakening `decision_responses_reject_update` or
rewriting the answer schema. A read followed by an unguarded write would allow
two Workers to win; the database unique key is the arbiter. Enforced taps are
the proof role expressly allowed by `CODE-VS-JUDGMENT.md`.

## Deployment order and limits

Prefer **migration 0040 first, gateway deploy second**. It only adds a table and
triggers, leaving existing rows and old readers unchanged. Old code still has
the old replay behavior until replaced. Deploying the new code first is safe
against unauthorized execution but temporarily refuses tier-3 actions: the
missing-table error reaches the core's existing safety-check refusal. Tier 1
and tier 2 do not consult the claim store. Applying 0040 then enables claims.
The local rollout test covers both compatibility boundaries.

Existing taps may already have been used by old code, which recorded no claim.
Before opening tier-3 actions after cutover, let the ten-minute window for old
taps expire and obtain fresh confirmations. Keep this in the owner rollout.
Rolling back to old code also restores the old replay behavior even if the new
table remains. Do not remove the consumption table to retry a failed action.

No migration was applied remotely, no gateway was deployed, no real call or
Telegram action ran, and no external tool side effect was exercised. The
cross-channel test uses independent real gates over local D1 and a real
decision-service answer from a Telegram identity. Live acceptance and remote
D1 rehearsal remain owner actions. The separate queued second-autonomy-evaluation
verdict issue is unchanged by this slice.
